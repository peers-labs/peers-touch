# Desktop Provider / Model 对齐执行计划

## 1. 目标

- 把 Provider / Model 体系从“少量内置协议 + 命令层直连实现”推进到“配置驱动注册表 + 协议适配层 + 模型能力约束”。
- 保持命令层稳定，让协议差异尽量收敛在适配层而不是扩散到 UI 和调用方。
- 为后续接入 Station 真源同步、本地持久化与协议回归测试预留稳定边界。

## 2. 当前问题

- Registry 数据仍以内置预设为主，用户覆盖与远端同步边界还不完整。
- 协议差异主要聚集在实现细节里，命令层与协议层尚未完全解耦。
- 能力字段虽然已经被识别为统一约束对象，但还没有贯穿 UI、运行时校验与模型发现流程。

## 3. 依赖顺序

### 3.1 Registry 归一化

- 统一 `ProviderRecord` / `ModelRecord` 的输入源与归并规则。
- 明确内置预设、用户覆盖、本地持久化、远端同步的优先级。
- 先稳定注册表边界，再推进协议扩展。

### 3.2 Protocol Adapter 扩展

- 把协议差异继续收敛到 `Protocol Adapter` 层。
- 补齐主流厂商协议族的错误映射、能力识别与请求构造差异。
- 保持命令层接口不因协议扩展而发生语义漂移。

### 3.3 Model Adapter 接管能力差异

- 让模型级特性由 `Model Adapter` 统一表达。
- 让 `function_call`、`reasoning`、`vision`、`structured_output` 等字段同时驱动：
  - UI 展示
  - 运行时校验
  - 远端模型发现后的能力归并

### 3.4 持久化与同步分层

- 本地持久化只负责用户设备内覆盖与缓存。
- Station 同步只负责共享真源和跨端对齐。
- 两者都不能直接绕开 Registry 归并规则。

### 3.5 可观测与回归

- 为协议适配层建立隔离测试靶。
- 为命令层建立与协议无关的稳定回归用例。
- 为关键 Provider 建立契约校验与错误映射回归。

## 4. 交付物

- 配置驱动的 Provider Registry 归并规则
- 分层的 Protocol / Provider / Model Adapter 边界
- 统一能力字段规范及消费路径
- 本地持久化与 Station 同步的边界约束
- 可重复执行的协议契约测试与命令层回归测试

## 5. 验收标准

- 新增 Provider 时不需要改动命令层语义。
- 同一 Provider 可在不改 UI 协议判断的前提下切换不同协议适配器。
- 能力字段能够被 UI、运行时校验与模型发现流程共同消费。
- 本地覆盖与远端同步不会绕开 Registry 归并规则。
- 协议扩展后可以通过隔离测试验证，不依赖手工页面回归。
