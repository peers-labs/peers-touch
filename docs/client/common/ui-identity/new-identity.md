# Peers Touch 新 UI Identity

## 1. Document Scope

本文档定义：

- Peers Touch 新一代客户端 UI Identity 的总纲。
- 为什么现有 UI Identity 能维持一致性，但不足以稳定产出高质量视觉结果。
- 新 UI Identity 的北极星、表达模型、自由度模型、页面分型与验收标准。
- 后续重写 `foundations`、`tokens`、`layout`、`components`、模块文档时应遵守的上游方向。

本文档不定义：

- 具体 Desktop / Mobile 组件实现细节。
- 具体 token 数值。
- 单一模块的完整页面规范。
- 某一张页面的最终视觉稿。

---

## 2. 为什么需要一套新的 UI Identity

现有 UI Identity 已经解决了一个重要问题：

- 它能避免页面像临时拼装出来的组件集合。
- 它能约束跨模块的一致性。
- 它能把 federation、identity、trust、privacy 这些产品事实纳入界面表达。

这说明现有体系在“防跑偏”上是有效的。

但它仍然存在一个关键缺口：

- 它更擅长约束“不要做错”，不够擅长生成“怎样才会做得高级”。

当前暴露出的典型问题：

1. **统一但平**
   - 页面不乱，但也不够有记忆点。
   - 能做到克制，却很难做到高级。

2. **约束强，生成弱**
   - 文档里有大量 `不要`、`禁止`、`不能像 dashboard`。
   - 但缺少足够强的“应该长什么样”的正向设计范式。

3. **模块虽有约束，但自由度模型不清晰**
   - 文档承认模块需要各自 refinement。
   - 但没有清楚定义哪些层必须继承，哪些层允许发散，发散的边界是什么。

4. **入口页与常规业务页没有被明确区分**
   - 登录、onboarding、首次进入这类页面承担品牌第一印象。
   - 但如果它们和普通业务页使用同样强度的克制规则，最终容易只剩“礼貌”，缺少吸引力。

因此，新 UI Identity 的目标不是推翻“统一性”和“可验证性”，而是补齐：

- 品牌识别
- 审美决断
- 模块自由
- 表达强度分级

---

## 3. 新的北极星

Peers Touch 新 UI Identity 采用：

**Structured Expressive Minimalism**

中文可表述为：

**结构化表达极简**

它由四个关键词构成：

### 3.1 Structured

界面不是自由生长，而是在统一结构内展开。

它要求：

- 共享信息层级。
- 共享边界哲学。
- 共享动作优先级。
- 共享 trust / source / audience 的表达语义。

### 3.2 Expressive

Peers Touch 不应只“正确”，还应“可被识别”。

它要求：

- 产品必须具备清晰的品牌视觉识别。
- 模块必须在受控范围内拥有自己的表情与个性。
- 入口页、品牌页、核心流程页允许不同表达强度。

### 3.3 Minimalism

极简不是稀薄，也不是删到没有气质。

它要求：

- 减少竞争性结构，而不是减少信息。
- 用比例、留白、层级、材质、对比替代堆装饰。
- 一个页面必须有一个明确主角。

### 3.4 Trust-aware

Peers Touch 是联邦化产品，信任与来源必须在相关时被看见。

它要求：

- trust / station / identity / audience 继续是产品事实，而不是调试信息。
- 这些事实只在影响理解与动作时升权表达。
- “可验证”不等于“像协议控制台”。

---

## 4. 新 UI Identity 的核心判断

今后的页面，必须同时满足以下四件事：

1. **一眼能看出这是同一个产品**
2. **一眼能看出这个模块有自己的气质**
3. **一眼能看出当前最重要的动作是什么**
4. **在需要时，能看懂信任与来源，但不会被系统元信息压住**

如果一个页面只满足第 1 和第 4 条，它会显得“正确但平”。

如果只满足第 2 条，它会变成“有个性但不成系统”。

新体系要求四者同时成立。

---

## 5. 设计系统的四层模型

新 UI Identity 不再只用“通用规范 + 模块 refinement”来组织，而是明确拆成四层：

### 5.1 不可变层

所有模块必须继承，不能各自改写：

- 信息层级原则
- 动作优先级
- trust / source / audience 的表达语义
- 边界哲学
- 基础 token 语义
- 可访问性与状态 ownership

这是“同一个产品”的底盘。

### 5.2 共享语法层

所有模块共享，但允许不同强度：

- 空间节奏
- 圆角家族
- 深浅层级
- 阴影与边框的使用原则
- 主要 CTA 的结构语法
- 标题与元信息的对比关系

这是“同一种设计语言”的语法。

### 5.3 模块包络层

每个模块必须声明自己的可调范围：

- 内容密度
- 视觉重量
- 元信息压缩程度
- 情绪温度
- 插画 / 图形 / 动效的允许度
- 页面中的主视觉类型

这层不定义具体稿子，定义的是模块的“自由边界”。

### 5.4 签名特征层

模块可以拥有自己的签名表达，但必须满足全局识别：

- 一种主视觉母题
- 一种空间关系偏好
- 一种重点对比方式
- 一种品牌气质的体现方式

这层决定“看起来像 Peers Touch 的哪个部分”，而不是“看起来像另一个产品”。

---

## 6. 自由度模型

为了保证“引导与发散并存”，每个模块在设计前必须明确回答下面三类问题。

### 6.1 哪些是必须继承的

必须继承的内容包括：

- trust 语义
- 页面层级逻辑
- CTA 优先级
- token 语义
- 组件边界 ownership

这些决定产品一致性，不能模块自定义。

### 6.2 哪些是允许调节的

允许模块调节的内容包括：

- 密度
- 视觉对比强度
- 卡片权重
- 图形存在感
- 动效存在感
- 文案语气

这些决定模块气质，可以不同，但必须声明范围。

### 6.3 哪些是允许创造的

允许模块创造的内容包括：

- 模块签名图形语言
- onboarding / empty / entry 页的情绪表达
- 模块级 hero 构图
- 模块级强化状态的视觉模式

这些内容的存在，不是例外，而是新体系中的正式一层。

---

## 7. 表达强度分级

不是所有页面都应该一样克制。

新 UI Identity 要求每个页面先归类，再决定视觉表达强度。

### 7.1 Brand Entry Surfaces

适用页面：

- 登录
- onboarding
- 首次进入
- 品牌入口页

目标：

- 建立第一印象
- 建立信任
- 建立品牌记忆

要求：

- 允许比常规业务页更强的视觉主张。
- 必须有明确主角和品牌记忆点。
- 允许氛围层，但不能喧宾夺主。

### 7.2 Core Workflow Surfaces

适用页面：

- social feed
- chat
- settings
- search
- notes

目标：

- 高频使用
- 低噪音
- 长时间可读

要求：

- 结构稳定优先。
- 克制优先。
- 模块个性通过细部，而不是靠大幅图形。

### 7.3 Trust / Recovery Surfaces

适用页面：

- 权限受阻
- session 过期
- degraded / unavailable / blocked

目标：

- 快速理解问题
- 明确 authority
- 提供恢复路径

要求：

- 视觉等级与问题等级严格成比例。
- 不允许把严重问题做成轻装饰，也不允许把普通提示做成重事故。

### 7.4 Tool / Admin-like Surfaces

适用页面：

- cron
- provider management
- system-like configuration panels

目标：

- 高可用
- 高效率
- 明确边界

要求：

- 可更理性，但仍然不能滑向通用后台审美。

---

## 8. 品牌识别不再缺席

旧体系的问题之一，是有产品原则，但品牌识别偏弱。

新体系要求 Peers Touch 必须具备可被识别的视觉母语。

### 8.1 品牌识别应该来自哪里

应来自：

- 比例关系
- 空间秩序
- 单一重点色的出现方式
- 材质与层级控制
- 模块签名图形的抽象母题

不应主要来自：

- 彩色堆叠
- 到处发光
- 复杂装饰纹理
- 组件库默认样式的拼接

### 8.2 品牌识别的判断标准

如果把 logo 拿掉，一个页面仍应让人感到：

- 它属于 Peers Touch
- 它不是 generic SaaS
- 它不是 admin dashboard
- 它不是 web3 风的通用套板

---

## 9. 登录页应被重新定义

Auth 不应只被定义为“认证页面”，而应被定义为：

**品牌入口界面**

这会直接改变它的设计标准。

### 9.1 登录页必须承担的任务

- 告诉用户这是哪个产品
- 告诉用户你将以谁的身份进入
- 告诉用户你进入的是哪一个站点 / 网络环境
- 告诉用户当前连接是否可信
- 让用户毫不犹豫地看到唯一下一步动作

### 9.2 登录页不应该继续停留在的状态

不应该是：

- 一个很规矩的表单卡片，加一层“解释联邦网络”的背景装饰

这会让页面功能正确，但品牌感不足。

### 9.3 新登录页的设计原则

登录页必须满足：

1. **主卡片是绝对主角**
   - 尺寸、对比、排版、按钮都要让主任务一眼成立。

2. **背景只能是氛围，不是可玩具**
   - mesh 是世界观解释层，不应成为探索型交互主角。
   - 默认状态下不应鼓励 hover 探索、信息弹层、复杂路径理解。

3. **PIN 区域必须像安全界面，而不是普通表单**
   - 它应该更精确、更高级、更具仪式感。

4. **品牌记忆点必须来自整体秩序，不来自零散花活**
   - 不是多做几种 hover、几张 frosted 卡片、几种紫色层级。

5. **入口页允许比普通业务页更强的视觉表达**
   - 但表达必须围绕“身份进入”与“可信连接”展开。

---

## 10. 对当前登录页问题的归因

如果按照新 UI Identity 来看，当前登录页的问题不只是“实现不够好”，而是暴露了旧体系的边界。

主要问题：

1. **宏观方向是对的，审美力度不够**
   - 有主卡片、有背景、有 trust 语义，但整体偏中庸。

2. **背景层承担了过多存在感**
   - 它名义上是 calm backdrop，实际上已经带有较强的可探索属性。

3. **页面在克制与炫技之间摇摆**
   - 一边强调 restraint，一边又加入 hover mesh、侧向 panel、发光、provider 强高亮等局部动作。

4. **缺少一个真正成立的品牌记忆点**
   - 不是丑，也不是乱，而是不够“像自己”。

5. **入口页没有获得比常规业务页更高的表达权限**
   - 所以最终只能做到“干净”，很难做到“惊艳”。

## 11. 新体系下的验收标准

今后评审页面，不再只问“有没有违例”，还要问“是否成立”。

每个页面至少要回答：

### 11.1 系统一致性

- 是否仍然明显属于 Peers Touch？
- 是否仍然遵守 trust / action / hierarchy 的基础规则？

### 11.2 模块个性

- 是否能看出这是 auth / social / chat / settings，而不只是同一套组件换文案？

### 11.3 主角是否成立

- 页面是否存在明确主角？
- 用户第一眼是否知道最重要的动作和最重要的信息？

### 11.4 品牌记忆是否成立

- 页面是否有自己的视觉记忆点？
- 这种记忆点是整体性的，而不是碎片化装饰？

### 11.5 克制是否有力量

- 页面是否是“克制但高级”？
- 还是只是“克制但偏平”？

## 12. 对后续文档重写的要求

这份新总纲确认后，后续文档需要同步重写：

1. `foundations.md`
   - 从“Quiet Protocol Minimalism”切换到新的北极星。

2. `tokens.md`
   - 增加“表达强度”和“品牌识别用途”的说明。

3. `layout.md`
   - 增加入口页、常规流程页、恢复页、工具页的页面分型规则。

4. `components.md`
   - 增加“组件语法统一，但表达强度可分级”的约束。

5. `modules/auth/README.md`
   - 将 auth 明确升级为“品牌入口模块”。

6. `modules/social/README.md`
   - 保留 Human-first，但增强模块个性表达方式。

---

## 13. 迁移原则

新 UI Identity 的落地不应一次性翻掉所有页面，而应按以下顺序推进：

1. 先重写总纲。
2. 再重写 auth 模块，作为新体系的第一个品牌入口样板。
3. 再重写 social 模块，验证“统一 + 模块个性”是否能同时成立。
4. 最后再把 token、组件、review checklist 完整收口。

这样做的原因是：

- 登录页最容易暴露“统一但平”的问题。
- social 最容易验证“高频使用下是否还能保持个性和秩序”。

---

## 14. 一句话原则

Peers Touch 新 UI Identity 的目标，不再只是：

- 保证页面别跑偏

而是：

- **让页面在统一之内有个性，在克制之内有力量，在可信之内有吸引力。**
