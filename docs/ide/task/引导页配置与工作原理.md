### 一、整体架构概览

Desktop 端引导系统采用 **双模式架构**，支持两种引导流程：

1. **Default 模式** (`OnboardingPage`) -- 内置的硬编码 5 步引导
2. **Wizard 模式** (`WizardRenderer`) -- 配置驱动的动态向导，步骤从后端 API 获取

应用启动时在 [App.tsx](../../../apps/desktop/src/App.tsx#L37-L38) 中定义了状态类型：

```typescript
type AppState = 'loading' | 'onboarding' | 'ready';
type OnboardingMode = 'default' | 'wizard';
```

### 二、入口与状态管理

#### 1. 应用启动流程 ([App.tsx:L136-L151](../../../apps/desktop/src/App.tsx#L136-L151))

```typescript
useEffect(() => {
    Promise.all([api.getOnboarding(), api.getWizard()])
      .then(([state, wizard]) => {
        if (state.completed) {
          setAppState('ready');
        } else {
          setOnboardingMode(wizard.available ? 'wizard' : 'default');
          setAppState('onboarding');
        }
      })
      .catch(() => {
        setAppState('ready');
      });
  }, []);
```

启动时并行调用 `getOnboarding()` 和 `getWizard()` 两个 API：
- 若 `state.completed === true`，直接进入 `ready` 状态
- 否则检查 wizard 是否可用，决定使用哪种引导模式

#### 2. 引导页渲染分支 ([App.tsx:L245-L258](../../../apps/desktop/src/App.tsx#L245-L258))

```typescript
if (appState === 'onboarding') {
    if (onboardingMode === 'wizard') {
      return (
        <GlobalLayout sideNav={null}>
          <WizardRenderer onComplete={() => setAppState('ready')} />
        </GlobalLayout>
      );
    }
    return (
      <GlobalLayout sideNav={null}>
        <OnboardingPage onComplete={() => setAppState('ready')} />
      </GlobalLayout>
    );
  }
```

## 二、工作原理详解

### 整体流程图

```
应用启动 (App.tsx)
    │
    ├─ 并行请求 ──┬── api.getOnboarding()  → { completed: true/false }
    │              └── api.getWizard()       → { available: true/false, config: WizardConfig }
    │
    ├─ completed === true ?
    │   └── YES → appState = 'ready' → 直接进入主界面
    │
    └─ NO → 进入引导
        │
        ├─ wizard.available === true ?
        │   └── YES → onboardingMode = 'wizard' → 渲染 WizardRenderer
        │
        └── NO → onboardingMode = 'default' → 渲染 OnboardingPage
```

### 1. 启动判断阶段

[App.tsx](../../../apps/desktop/src/App.tsx#L136-L151) 中，应用启动后并行调用两个 API：

- `api.getOnboarding()` — 检查用户是否已完成过引导
- `api.getWizard()` — 检查是否有可用的 Wizard 配置

如果引导已完成，跳过直接进入主界面；否则根据 Wizard 是否可用选择引导模式。如果两个请求任一失败，**容错为直接进入 ready 状态**。

### 2. Default 模式运行

[OnboardingPage](../../../apps/desktop/src/pages/OnboardingPage.tsx) 使用 `useState(0)` 跟踪当前步骤，用户通过 `onNext` / `onBack` 在 5 步之间导航。

**状态持久化**：每步完成时调用 `api.setOnboarding(data)` 将选择保存到后端：
- Step 2 完成 → `api.setOnboarding({ interests: [...] })`
- Step 3 完成 → `api.setOnboarding({ language: 'en' })`
- Step 4 完成 → `api.setOnboarding({ completed: true })` → 触发 `onComplete()` → `setAppState('ready')`

### 3. Wizard 模式运行

[WizardRenderer](../../../apps/desktop/src/components/wizard/WizardRenderer.tsx) 启动时：
1. 并行请求 `getWizard()` + `getWizardState()` 获取配置和上次进度
2. 如果有保存的进度（`state.current_step` 和 `state.context`），恢复到上次位置
3. 根据 `step.type` 动态渲染对应组件
4. 每步完成调用 `api.saveWizardStep(stepId, data)` 保存
5. 最后一步调用 `api.completeWizard()` 完成整个向导

### 6. 总结要点

1. **Desktop App 目前没有独立的 Email/Password 登录 UI 组件**。`loginWithPassword` 方法存在于 `useOAuth2Store` 中，API 和 Rust BFF 层已完整实现，但前端未有对应的表单组件（仅在 docs 原型和 Flutter 客户端中存在）。

## 架构审计：Desktop 端日志能力缺失根因分析

### 一、规范 vs 实现的差距

你们的 [统一运行时存储架构规范](../../../docs/architecture/storage/unified-runtime-storage-architecture.md) 定义了非常清晰的要求：

| 规范条目 | 要求 | Desktop 实际 | Station 实际 |
|---------|------|-------------|-------------|
| `logs` 目录语义 (§4) | 运行日志与审计，中周期，顺序写 | ✅ 目录被创建 | ✅ 目录被创建 |
| 启动初始化 (§8.1) | 必须创建六类目录 | ✅ `initialize_app_storage` 正确创建 | ✅ `EnsureAppDirs` 正确创建 |
| 可观测性 (§10) | 必须输出统一存储观测指标、治理日志 | ❌ **完全缺失** | ✅ Logrus + 文件持久化 + 轮转 |
| 迁移日志 (§8.3) | 迁移日志必须进入 logs | ⚠️ 仅 `storage-migration.jsonl` | ✅ |
| 编码标准 (coding-standards.md) | 禁止裸 `print`/`println`，必须使用日志框架 | ❌ **无日志框架** | ✅ `Logger` 接口 + Logrus 实现 |

### 二、根因：Desktop 端缺失「日志基础设施层」

问题不在目录——**`logs/` 目录已正确创建**（[initialize_app_storage](../../../apps/desktop/src-tauri/src/infrastructure/storage/mod.rs#L70-L76) 会在启动时创建所有六类目录）。

根因是 **Desktop Rust 端根本没有日志框架**：

1. **`Cargo.toml` 中无日志依赖**：没有 `tracing`、`env_logger`、`log`、`tauri-plugin-log` 中的任何一个
2. **`main.rs` 中无日志初始化**：只注册了 `tauri_plugin_deep_link`，没有日志 plugin
3. **`AppState` 中无 `StorageLayout`**：[AppState](../../../apps/desktop/src-tauri/src/state/mod.rs#L22-L26) 只有 `session/settings/realtime`，**没有持有 `StorageLayout`**，意味着：
   - `logs/` 目录路径虽然在启动时被决议了，但 **没有传入全局状态**
   - 后续所有模块无法获知日志应该写到哪里
4. **`initialize_app_storage` 无人调用**：搜索整个代码库，只有模块定义处有这个函数，**main.rs 没有调用它**

这形成了一个讽刺的局面：**存储框架代码写好了、目录结构定义好了、六类目录的枚举和路径决议都实现了，但启动流程跳过了它，日志框架也从未接入。**

### 三、对比 Station 端的正确做法

Station (Go) 端有完整的三层日志体系：

```
Logger 接口 (core/logger/logger.go)
  ↓
Logrus 实现 (core/plugin/logger/logrus/logrus.go)
  ↓ 配置
log.yml → 控制级别、持久化开关、文件大小、轮转策略
  ↓ 目录
AppLogsDir() / appdir.Resolve("station", "logs") → 实际写入路径
```

Station 做到了：Logger 接口 → 具体实现 → 配置驱动 → 目录决议 → 文件持久化 → 日志轮转。

### 四、方案

Desktop Rust 端需要补齐的**不是一个 fix，而是一个基础设施层**。对标 Station 的三层体系，Desktop 需要：

| 层 | 要做的事 | 说明 |
|---|---------|------|
| **① 启动初始化** | `main.rs` 中调用 `initialize_app_storage("desktop")` 并将 `StorageLayout` 挂入 `AppState` | 这是最基础的——让全局状态知道目录在哪 |
| **② 日志框架** | 引入 `tracing` + `tracing-appender`（或 `tauri-plugin-log`） | `tracing` 是 Rust 生态的标准日志/追踪框架，与 Tauri 2.0 兼容 |
| **③ 日志写入** | 初始化 `tracing-appender` 指向 `StorageLayout.dirs[Logs]`，JSON 格式，配日志轮转 | 对标 Station 的 Logrus + Lumberjack |
| **④ `logs_tail` 实现** | 真正读取日志文件，替换当前 stub | 让前端 LogsTab UI 能展示日志 |
| **⑤ 全局 `info!` / `warn!` / `error!` 替换** | 在所有 application 模块中用 `tracing` 宏替换目前的哑操作 | 长期工作，分步推进 |

**具体技术选型建议**：

- 推荐 `tracing` + `tracing-subscriber` + `tracing-appender`，这是 Rust 生态的事实标准
- 不推荐 `tauri-plugin-log`（它封装太重，且日志路径不走你们自己的存储框架决议）
- 日志格式建议 JSON lines（`.jsonl`），与前端 `LogsTab` 已有的 JSONL 解析能力对齐

  4. 如果有新连接且是 active → `onComplete()`
- **❓ 关键问题**：用户没有完成登录，`loadAll()` 后 connections 数量应该没变。所以 `hasNewConnection` 应该是 `false`，不应该跳到主页。

  **但是！** 来看 `loadAll` 的实现（store L73-86）：它有**去重机制**—— `if (loadAllPromise) return loadAllPromise`。如果 LoginPage 的 `useEffect`（L41-43）的 `loadAll()` 还没完成，而此时 `handleOAuthConnect` 里读了 `connections.length = 0`（因为第一次 loadAll 还没返回），那么 `connectionsBeforeRef.current = 0`。然后用户点 X → `handleOAuthModalClose` → 又调 `loadAll()`，这次 connections 被填上了，`currentConns.length = 1 > 0 = prevCount` → **误判为新连接** → `onComplete()`！

  这就是 **竞态条件 (race condition)** 的根因。

#### 路径 F：OAuth2ConnectModal → idle 状态 → 点击「使用 GitHub 登录」
- **触发**：`handleSignIn` (OAuth2ConnectModal L35-54)
- **逻辑**：调 `startAuth(provider.id)` → 等待 poll → 成功后设 `authState='success'`
- **✅ 正确**（如果成功）

#### 路径 G：OAuth2ConnectModal → success 状态 → 点击「Done」
- **触发**：`onClick={onClose}` (OAuth2ConnectModal L117)
- **逻辑**：触发 `handleOAuthModalClose`
- **分析**：此时 `startAuth` 已经在内部调了 `loadAll()`，connections 已更新。`currentConns.length` 确实多了一个。`hasNewConnection = true`，有 active → `onComplete()`
- **✅ 正确**

#### 路径 H：OAuth2ConnectModal → error 状态 → 点击「取消」
- **触发**：`onClick={onClose}` (OAuth2ConnectModal L134)
- **逻辑**：同路径 E
- **❓ 同样的竞态问题**（但此时 `startAuth` 失败，connections 没增加，通常 OK）

#### 路径 I：OAuth2ConnectModal → error 状态 → 点击「重试」
- **触发**：`onClick={handleSignIn}` (OAuth2ConnectModal L136)
- **✅ 正确**

#### 路径 J：OAuth2ConnectModal → waiting 状态
- **无按钮**，用户只能等待或关闭（X/遮罩 → 路径 E）
- **❓ 但这里有更严重的问题**：`startAuth` 在内部有一个 Promise 在 poll。如果用户关了 modal，`startAuth` 的 interval 还在跑。如果恰好此时 poll 成功了 → 内部 `loadAll()` → connections 增加了 → 然后 `handleOAuthModalClose` 的 `loadAll()` 发现多了一个 → `onComplete()`！

### 三、根因总结

**核心问题不是某一个按钮，而是 `handleOAuthModalClose` 的设计有架构性缺陷：**

1. **用"连接数量对比"来判断是否完成登录** — 这是一个 **间接信号**，容易被竞态条件干扰
2. **`connectionsBeforeRef.current` 捕获时机不可靠** — 如果 `connections` 还没加载完就被读取，值为 0，后续任何已存在的连接都会被误判为"新连接"
3. **关闭和成功走同一个 callback** — `onClose` 同时承担"取消"和"成功后确认"两种语义，无法区分

**正确设计应该是：明确区分"取消"和"成功完成"两个事件。**

## 修复方案

**核心思路：将 OAuth2ConnectModal 的 `onClose` 拆为两个语义明确的回调：`onCancel`（取消，回到登录页）和 `onSuccess`（成功，进入主页）。不再用"数连接数"这种间接方式判断。**

具体改动：

### 1. OAuth2ConnectModal —— 拆分回调

```typescript
interface Props {
  provider: OAuth2ProviderSummary | null;
  open: boolean;
  onCancel: () => void;     // 取消/关闭 → 回到登录选择
  onSuccess: () => void;    // 登录成功 → 进入主页
}
```

- `idle` 状态：X 按钮 / 遮罩 → `onCancel`
- `waiting` 状态：X 按钮 / 遮罩 → `onCancel`
- `success` 状态：「Done」按钮 → `onSuccess`
- `error` 状态：「取消」按钮 → `onCancel`；「重试」→ 重新 `handleSignIn`
- Modal 的 `onCancel` prop（即 X 按钮/遮罩）→ 根据 `authState` 决定走哪个

### 2. LoginPage —— 删掉 `connectionsBeforeRef` 和数量对比逻辑

```typescript
const handleOAuthCancel = useCallback(() => {
  setConnectProvider(null);
  // 仅关闭 modal，刷新下数据，留在登录页
  loadAll();
}, [loadAll]);

  setConnectProvider(null);
  loadAll().then(() => onComplete());

```

- `success` 状态下点 X → 用户已成功，应该走 `onSuccess`
- `waiting` 状态下点 X → 需要考虑中断 polling 的问题（但这个是 store 层面的，这次先不改）
