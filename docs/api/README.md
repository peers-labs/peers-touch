# 对外 API 合同（Public API Contracts）

> **Status**: active
> **Purpose**: 面向仓库**外部调用方**的 HTTP/集成合同唯一归属地。
> **Last updated**: 2026-10-12

本目录回答一个问题：**外部系统怎么稳定地调用 Peers-Touch**（端点、鉴权、请求/响应、
状态码、幂等、限流、示例）。它不解释系统内部为什么这么设计、由哪个子服务器实现。

## 1. 边界：什么放这里，什么不放

| 放 `docs/api/` | 不放（去对应层） |
|---|---|
| 外部可见的端点、方法、鉴权方式 | 内部子服务器划分、DDD、表结构、事务编排 → `docs/architecture/` |
| 请求/响应 wire schema、字段约束、枚举 | 内部事件总线 arm 编号、队列名、实现状态机 → `docs/architecture/` |
| 状态码语义、错误处理、重试/退避 | 单平台内部落地、目录组织 → `docs/client/`、`docs/station/` |
| 幂等键、限流配额、版本与稳定性承诺 | 编码风格/命名规范 → `docs/global/coding-guide/` |
| 可直接运行的 curl/SDK/webhook 示例 | 历史演进、被取代方案 → `docs/context/` |

规则：

1. **对外合同只在本目录定义一次。** 架构/平台文档需要提及时只放链接，不得内联复制合同正文，避免双真源漂移。
2. **不写内部实现名词。** 调用方不需要知道表名、子服务器、SSE arm 编号、聚合根；这些是内部事实，留在 architecture。
3. **合同必须与已上线行为一致。** 状态码、字段、上限、配额以 `model/domain/**/*.proto` 与线上实现为准；改合同等于改对外承诺，需同步代码并有 Journey/实测证据，禁止臆测数值。
4. **默认无官方客户端。** 合同以语言无关的 HTTP+JSON 表述并给 curl 示例；受维护的客户端/SDK 是 `apps/` 下的独立产品，不在本目录内虚构。

## 2. 目录约定

```text
docs/api/
├── README.md                 # 本规范 + 合同索引
└── <domain>/                 # 对外能力域，小写中划线
    └── <capability>.md       # 一个对外能力一份合同
```

- 示例：`message-publishing.md`。同一能力域有多个公开端点时按能力拆文件，不堆超长单页。
- 文件名用调用方视角的能力名，不用内部模块名。

## 3. 合同文档必备结构

每份合同使用统一骨架（小节可按需要裁剪，但语义不得缺）：

1. **头部元信息**：Status（active/deprecated）、稳定性与版本承诺、最后核验日期。
2. **心智模型 / 适用场景**：一段话说明这个能力解决什么。
3. **鉴权与获取凭证**：鉴权方案、凭证如何获得与轮换。
4. **端点与请求**：方法、路径、Header、body 大小/编码约束。
5. **请求 schema**：字段表（必填、类型、约束、枚举合法值），并链接到 proto 真源。
6. **成功响应**：字段与枚举（给真实示例）。
7. **错误与状态码**：状态码 + 响应体 + 调用方动作（重试/终态丢弃），鉴权失败不可区分性等安全语义。
8. **幂等、限流与重试**：幂等键与窗口、配额、`Retry-After`、退避建议。
9. **调用方责任 / SLA**：超时、失败处理等不依赖服务端的约束。
10. **可直接运行的示例**：curl 起步，按需给 CI / webhook 场景。

写作要求：事实准确优先于详尽；枚举给**线上实际接受的完整字符串值**；示例可直接复制运行。
