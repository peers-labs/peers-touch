# 产品验收准则

> Status: active
> Owner: Product / Architecture；各业务 Domain 提供具体 Journey、Oracle 和证据。

本准则约束产品能力的设计、实现与完成判断。Acceptance Core 校验证据合同；
业务 Owner 负责证明能力被真实使用，不能用框架检查替代产品消费。

## AC-PRODUCT-01：禁止孤岛功能

**判断一个功能是不是孤岛：有没有地方用它，它的产出有没有地方用。
如果两者都没有，就是孤岛，没有产品意义，不能通过验收。**

每项功能必须明确并验证：

1. **使用入口**：哪个用户角色，通过哪个真实产品入口，执行什么动作。
2. **产出消费方**：产出的配置、数据、授权或运行结果，由哪个既有功能、
   用户动作或外部接收方实际使用。
3. **消费闭环**：从入口，经生产与消费，到接收方可观察的结果；跨页面、
   跨端或跨服务时必须验证连接处，不能只分别验证两端存在。
4. **失败与撤回**：失败如何重试，禁用、撤权或删除后消费方如何响应，
   哪个 Owner 清理副作用。

两项都缺失是确定的孤岛。任一必需环节缺失、不可达或没有当前源码的真实
消费证据，都不能声称该产品能力已完成；对应范围保持 UNPROVEN。
源码检查、安装成功、配置保存、目录发现、截图或日志分别证明局部事实，
不能独立证明消费闭环。禁止用按钮文案、跳转链接或待实现的消费方代替消费。

## AC-PRODUCT-02：管理与普通用户消费边界

管理员负责配置、安装、凭据、验证和授权；普通用户只看到完成任务需要的
模型、个人默认值、使用结果和可操作的失败提示。内部 Provider、DM/CLI、
命令、部署或凭据细节不进入普通用户操作界面。

## AC-PRODUCT-03：权限必须覆盖实际消费

权限控制必须在实际消费的服务端 Owner 中执行，并覆盖下一次调用、恢复和
续执行。隐藏页面或客户端过滤不能替代权限；授权目录不能替代成功调用。

## Agent Provider 的业务验收应用

Dashboard 中，CLI 是 Provider 的接入方式之一，与 DM 共用配置、模型和
授权链路。管理员选择 Provider / DM 或 CLI → CLI 安装（如需）→ 配置连接
→ 验证实际模型调用 → 控制哪些用户可用 AI 及该 Provider 的模型 →
普通用户在 Desktop 选择模型/默认值 → 发起对话 → 收到真实模型结果。

安装产出必须被同一 Provider 的发现和调用消费；凭据与配置必须被 Station
的同一执行 Owner 消费；授权必须被 Desktop 目录及下一次实际调用消费。
DM 与 CLI 都需要允许、拒绝、撤权和失败恢复的接收方证据。
仅安装 CLI、仅展示静态模型或仅保存 Provider 不构成这项能力通过。
