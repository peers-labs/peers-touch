# 执行模型设计决策

> **Status**: draft
> **Created**: 2026-10-22 | **Updated**: 2026-10-22
> **Owner**: Acceptance

以下 ID 为本提案内局部引用；全部 proposed。
确认时合入现有 Acceptance 决策与治理投影，不创建第二套 active 决策真源。

## EM-01：将 Gate 判定与场景生产分开

**状态**：proposed。

**依据**：两个 interactions 标签复用相同运行体；Social/RAL 已存在一份
Suite、多份只读判定的模式。

**决策**：业务 case 产生稳定 assertion 证据，Gate 引用自己的所需集合。
一项场景可满足多项 Gate，判定仍彼此独立。

**理由**：降低物理重复执行，同时保留能力映射与每项结论的可追溯性。

**替代方案**：删除同名动作 Gate 会丢失故障/平台条件；
仅抽出 Python helper 仍会在每个调用者重跑完整 Journey。

**代价**：需显式定义 assertion ownership、引用和证据强度；
不能靠旧 Gate 大结果的一枚 PASS 代替这些要求。

**复核条件**：若拆分导致原 receiver/negative/cell 覆盖丢失，禁止切换，
修正映射后再验证。

## EM-02：以三类依赖编译执行图

**状态**：proposed。

**依据**：Catalog 仅有启动、环境等字段；Runner 逐 Gate 执行，
目前没有由该 Catalog 定义的基础证明拓扑顺序。

**决策**：运行前置、证明依赖、业务状态依赖分别声明；
Runner 解析显式范围后展开闭包并拓扑执行。

**理由**：上层场景能复用对应基础断言，失败能归属到真实上游，
无需在每个 Gate 复制登录/解密探测。

**替代方案**：按名字排序没有语义；让所有业务等待全部安全 Gate 会扩大范围；
上层成功自动将基础能力全标 PASS 会把正向例子冒充负向安全证明。

**代价**：需要维护真实依赖与失效条件。声明漂移必须被编译和运行检查拦截。

**复核条件**：任何基础依赖没有稳定 ID、owner 或可执行 producer 时保持
BUSINESS_INJECTION_REQUIRED/UNPROVEN；不得由 Core 猜补。

## EM-03：把外层资源生命周期收敛到 Suite owner

**状态**：proposed。

**依据**：现有 D-21 已规定 attach-only；外层 Gate 循环仍逐项准备和清理，
普通 Mobile 认证还夹带无条件 WebView restart。

**决策**：复用现有 Provisioner/RuntimeBinding/launch context，
按兼容的资源组准备一次。场景受限 attach；reset/替换由 owner 执行并计量。

**理由**：隔离属于账号、设备、存储与业务 namespace，不能把全量重建当隔离。

**替代方案**：全局共用一个登录态会串扰账号/平台；每 Gate 新环境稳定但成本重复；
只写 runtimeReuse 不约束真实调用，无法阻止复发。

**代价**：状态污染和取消恢复必须显式处理；破坏性 case 可能需要独立资源组，
不能追求所有 Gate 共享一套客户端。

**复核条件**：新 case 的资源或安全状态不兼容时形成新组；不放宽 identity 验证。

## EM-04：保留功能先行与正式证据生产边界

**状态**：proposed。

**依据**：R001-05/06 两种检查重复同一广泛命令；当前 Workflow 要求功能
Journey 在正式闭环之前，正式 proof 有独立身份与完整合同。

**决策**：开发执行聚焦 Journey；正式闭环执行选定 producer 图一次，
其后只读 Gate 判定。去掉两轮完全相同的广泛执行。

**理由**：功能反馈尽早发生，正式取证无需因 Gate 数量再复制相同场景。

**替代方案**：一律把开发记录改标正式 proof 不满足合同；继续两轮广泛运行浪费；
完全取消功能先行会重新在不可用产品上消耗正式验收资源。

**代价**：聚焦功能 Journey 和正式 producer 仍可能各发生一次必要基础收发；
它们属于不同执行模式，不能承诺整个研发生命周期只发送一条消息。

**复核条件**：只有当前合同明确允许且从开始满足全部正式要求的输入，
才能供正式消费者验证；禁止事后人工追认。

## EM-05：用现有校验链防复发

**状态**：proposed。

**依据**：pipeline auditor 当前未解析入口实际执行图；Suite ledger 不能发现
绕过记账的启动/登录动作。

**决策**：扩展现有 structure validation、pipeline audit、Runner、Gap Detector，
核对注册 → 编译图 → 实际 dispatch/资源事件 → assertion 证据。

**理由**：唯一 owner 和确定性图检查比“下次注意”可复现。

**替代方案**：再建独立审批 Skill 会重复真源；
命令字符串去重会误判 RAL/Relay 的不同消费者；
只看耗时不能分辨缓存、缺步骤与真实复用。

**代价**：业务入口需可声明、可观测；未知动态执行不能自动加入共享图，
必须由其业务 owner 完成注入。

**复核条件**：检查无法识别入口或发现遗漏证明时 fail closed，
保留明确 missing/unsupported 状态，不以“优化”弱化验收。

## EM-06：把反馈时延和框架成本设为验收架构合同

**状态**：proposed。

**依据**：历史采样中 86/114 次运行 failed/blocked，两项 Social 占约 84.2%
的已记录时长；不同 Gate timeout 累加不能约束端到端反馈。

**决策**：采用 performance-design.md 的首次反馈、最终判定、冷/热态、
返工、取证与框架自身开销指标；设置 proposed SLO 和有界效率检查。

**理由**：成本可以归属、比较和阻止回退，产品缺陷也能通过快速正确定位提供价值。

**替代方案**：只缩短 timeout 会把慢产品变成更多失败；
只追求通过率会掩盖缺陷；只统计总时长不能区分排队、准备和反复调试。

**代价**：需完整计量和匹配样本；目前没有可宣称的 current-source P95。

**复核条件**：不足样本保留 UNPROVEN；SLO 改动需显式审查，
不能由控制器自行提高目标。

## EM-07：自优化只拥有合法执行策略

**状态**：proposed。

**依据**：现有重复生产、重复准备、宽泛重跑有可静态检查的合同关系；
required receiver/fault 与当前源码绑定不能因优化被移除。

**决策**：控制器自动选择复用、缓存、有限并行、节点排序和只读条件观察，
通过覆盖/隔离/失效约束，再以同候选样本比较效果；结构改变进入现有工作流。

**理由**：框架可以随真实成本优化，不需要每次让 Agent 阅读全部产物，
同时保留业务和证明真源。

**替代方案**：让 LLM 每次自由重写 Gate 不可复现且可能弱化证明；
只输出慢项列表没有形成“测量→选择→验证→反馈”的闭环；
自动跨源码继承 Native PASS 不符合当前证明合同。

**代价**：成本估计不保证全局最优；有界实验和回退需要保存合法策略身份。

**复核条件**：收益不足或证明质量下降就恢复前一合法策略。
优化器自身须有时间/资源预算，禁止递归验收和无界调优。

## EM-08：完整时间线与显式工具链边界

**状态**：proposed。

**依据**：Plan 探针停在没有独立 timeout 的 Python spawn；
当前解释器简单启动 probe 也超时，系统 Python 完成；
已有零散 durationMs 无法恢复整条准备/等待/取证链。

**决策**：使用 OTel 模型和既有 adapters 计量 span/事件；
显式选择满足依赖的工具链，对每次 RPC/child 加剩余 deadline，
确定性解析/构建使用内容和工具链输入缓存。

**理由**：及时判断“环境坏了、产品坏了还是验收坏了”，
减少不可恢复错误逐层耗尽大 timeout。

**替代方案**：只提高 Plan timeout 不能解决解释器边界；
把 YAML 当 JSON 或跳校验会产生错误结论；自建通用 tracing 框架增加维护成本。

**代价**：观测、缓存与 snapshot 检查本身要计量，且不能偷换 required artifact。

**复核条件**：输入、目录依赖或工具链变化即失效；
来源不明的缓存、旧 Native proof 或缺失计量不得作为性能通过依据。

## 架构审查

已做独立的 findings-first 自查：

- 把 `send` 与安全证明等价会过度推断：设计已要求逐 assertion/case 验证。
- 直接提升功能记录会违反正式取证时序：默认改为正式 producer 新运行。
- 同 environment 全部共享会串扰：采用兼容资源组与状态转换边界。
- 每个 Gate 发布部分成功会违反 D-21：采用 Suite 私有结果与原子发布。
- 单靠事件名称无法证明真实动作：要求执行边界计量和 artifact 关系。
- 核心理解具体业务会破坏 domain-neutral：业务提供 producer/Steps/oracles，
  Core 仅处理图、接口、校验和生命周期。
- 把 failed/blocked 比率当 flaky rate 会错判：历史成本与失败归因分开。
- 缩短负向窗口或 Gate timeout 不能代替成本优化：保留业务时序和硬证据。
- 静态图最长路径不包含设备串行：加入资源冲突与真实 queue 时间。
- 父子 span 相加会夸大成本：采用 exclusive time 与时间区间并集。
- 快反馈不能提前发布子 PASS：provisional 观察与 D-21 终态发布分开。
- 性能检查不能要求产品必须正常才“发现故障成功”：
  产品 FAIL 和失败反馈 SLO 独立，保留全部要求的因果记账。

草案可供用户确认；运行效果、产品 P1 回归与落地代码尚未证明。
