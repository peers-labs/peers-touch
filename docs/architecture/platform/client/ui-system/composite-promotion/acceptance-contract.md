# 已确认原型 UI 直接接入生产：目标与验收

> **Status**: 已确认，搜索试点执行中
> **Version**: v0.1.0
> **Created**: 2026-11-27 | **Updated**: 2026-11-27
> **Owner**: Client Platform / UI System
> **目标状态**: 用户已同意按本文执行完整搜索浮层试点；结果以实际证据为准

## 已确认的目标

用户在 2026-11-27 明确确认：

> 验收重点就是证明确认后的原型 UI 可以原样接进生产，而不是只证明共用零件。

这项工作面向原型设计者、生产接入者和验收者：原型从开始就按可接生产的方式编写，
确认后保留完整 UI 实现，由生产接入提供真实数据与业务动作。原型修改一次，
生产消费同一修改，不需要再照着原型重写布局、样式和交互。

此目标记为 `UI-PROMOTION-01`。[设计重评](./design-reassessment.md)必须满足它。
搜索、身份卡、会话轨是候选验证对象；它们的组件复用数量和测试数量不构成目标。

## 验收对象先确定到完整界面

每个接入对象都要能从原型真实入口打开，并对应生产实际功能入口。实施前记录：

| 必须确定的内容 | 记录要求 |
|---|---|
| 确认基线 | 用户确认的具体原型版本、入口、完整 UI 区域；不能只引用 Gallery 的整体 `confirmed` 标记。 |
| 生产入口 | 实际页面、弹层或面板及其启动方式；用组件展示页替代实际功能入口不能验收。 |
| 保留的 UI | 布局、信息层级、样式、文案含义、交互、可见状态、动效、焦点和退出/返回行为。 |
| 接入内容 | 原型样本与模拟动作分别换成哪些现有接口、业务投影和真实动作。 |
| 对照条件 | 同一套样本值和数据格式、同一操作过程、主题、语言、窗口内容尺寸和状态。 |
| 差异 | 原型缺陷、现有生产功能差异或平台约束逐条列明；影响已确认 UI 的调整需明确确认，不能由接入层自行简化。 |

“完整”指上述确定的界面范围。例如选择搜索浮层，就包含输入、结果、快捷项、
空态、提示、打开/关闭及键盘操作，不能完成结果行后把其余部分从验收中移除。
这不自动把整个应用、所有原型或所有平台加入本次范围。

尚未出现在确认基线中的真实业务状态，如加载、部分结果、失败、离线或重试，
要先补成可体验的原型状态，再作为生产接入依据。新增状态不能在生产另造一套 UI。

## 用户怎样验

Agent 先准备并自查两个可操作的入口，再交给用户对照。验收按下面三个过程进行：

| 验收过程 | 用户操作 | 应当看见的结果 | Agent 提供的证据 |
|---|---|---|---|
| `UI-AC01` 同样本完整对照 | 从原型和 Native Desktop 实际功能入口打开同一界面，按同一脚本操作。 | 同一对象、顺序、文字和计数；完整布局、状态与交互对应确认基线，动作后到达相应结果。 | 单一来源的样本和格式；两端对应的场景、对象 ID、截图与交互记录。 |
| `UI-AC02` 一处修改同时生效 | 在可还原的验收工作区，修改共享 UI 的一个已约定可见细节，刷新或重建两端，再还原。 | 原型和生产同时出现同一改变，父组件无需各改一遍。 | 实际入口到同一 UI 源文件的引用链、唯一修改的 diff、两端前后结果和还原记录。 |
| `UI-AC03` 真实业务闭环 | 生产使用真实业务数据，在同一 UI 内执行动作，退出、返回或再次打开核对结果。 | 仍是已确认的 UI；操作真正执行，结果能读回，失败可恢复，返回位置与状态正确。 | 当前源码的 Native Desktop Journey、接口/动作对应关系及业务结果读回。 |

同样本对照可以使用验收环境，不能给发布版本添加假数据切换入口。若需要在真实
业务中创建样本，由既有域 Acceptance fixture 从同一份合成数据创建，再沿生产
接口读取。仅在测试中给展示 props 喂值，可以诊断布局；它不能单独核销 `UI-AC01`
的实际入口对照，更不能核销 `UI-AC03` 的真实业务闭环。不需要为对照另搭模拟服务。

`UI-AC02` 证明同源；`UI-AC01` 证明完整 UI 保真；`UI-AC03` 证明生产接入有效。
三者都需要，不能用同源代码或两张静态截图代替完整接入。

## 完整状态和动作的检查

按所选界面的适用状态填写，每项映射到确认基线和两端操作证据。没有适用状态时
写明原因；缺少证据时标记 `UNPROVEN`，不能按默认截图通过。

| 检查维度 | 检查内容 |
|---|---|
| 正常使用 | 初始展示、输入、选择、提交、成功反馈、关闭、重新打开和返回；每个可用动作都有实际结果。 |
| 非正常状态 | 空数据、无匹配、加载、部分结果、失败、保留输入、重试、失效和恢复；变化不破坏布局和上下文。 |
| 输入与焦点 | 指针、键盘、输入法、快捷键、焦点进入/移动/关闭恢复，以及导航后的焦点交接。 |
| 呈现条件 | 确认范围内的宽/窄尺寸、主题、语言与长内容；比较完整区域及遮罩、菜单等关联浮层。 |
| 动效与稳定性 | 入场、退出、展开和滚动符合基线；减少动态效果、窗口隐藏/恢复后仍可操作，没有残留遮罩或透明面板。 |
| 可访问性 | 可访问名称、状态和禁用原因正确，键盘可完成主要过程；适用的辅助技术证据按项目规则提供。 |

同一技术栈和相同对照条件下，生产不能自行换布局、密度、样式或交互。字体栅格化
等运行时差异记录在对照中，不允许借此放宽明显的视觉偏差。不同平台的必要适配
逐项记录和评审，不把“原样接入”解释成所有设备必须共享同一套像素值。

项目规则见 [UI Identity](../../../../../client/common/ui-identity/README.md)、
[体验工艺](../../../../../client/common/ui-identity/craft-quality.md)及
[既有搜索原型合同](../prototype/components/global-search-overlay.md)。

## 交付和通过条件

Agent 负责启动与验证环境、准备样本、执行端到端、自查问题并整理结果。用户收到：

1. 原型入口与 Native Desktop 实际功能入口，以及本次对应的确认版本。
2. 按顺序可复做的操作脚本，每步写明应当看到什么。
3. 同一份样本、对应状态的两端证据和一处修改的同源证明。
4. 真实业务运行结果及完整差异清单。

只有 `UI-AC01`、`UI-AC02`、`UI-AC03` 和所选范围的必需状态均通过，且没有未解释、
未确认的 UI 差异，才能交付为“已确认原型 UI 已接入生产”。源码检查、组件测试、
import 路径和目录登记各自只提供局部证据。

搜索实施与实际证据见本轮工作报告。资料卡缺少双端实接、整轨未接入等历史
观察见[设计重评](./design-reassessment.md#基于实接入口的证据)，均不属于本轮完成声明。
