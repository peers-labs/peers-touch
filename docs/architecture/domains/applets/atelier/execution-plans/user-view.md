## 0. 怎么读这份文档

前面的 [feature-matrix.md](./feature-matrix.md) 是**自底向上**的（先底座、再往上），适合做对齐核对，但不适合"理解系统"。

这份文档反过来，**自顶向下**：

```
用户想干一件事（场景）
   → 工作台给他一个「功能块」（他能看到、能操作的东西）
      → 这个功能块由哪几步组成（用户视角的流程）
         → 每一步背后，底座做了什么（落到 F-XX 功能点）
```

读法：从一个场景进去，顺着往下读，就能从"用户体验"一路看到"底座实现"。每个功能块末尾的「底座支撑」就是它和 [feature-matrix.md](./feature-matrix.md) 的接口。

全文围绕 **7 个用户级功能块（U1–U7）** 展开，对应工作台从外到内的 7 件事。

---

## 1. 用户视角的全景：我在工作台里做什么

一个用户打开 Atelier，他脑子里不是"状态机""Provider"，而是这样一条线：

```
我说一个目标
  → 工作台帮我把它想清楚、拆成计划（U1 提目标 / U2 看计划）
  → 它自己开干，我能看到它在干什么（U3 看它干活）
  → 干得对不对它自己会查、会修（U4 质量与自动修复）
  → 它卡住了 / 要冒险了，才来问我（U5 该问我时才问我）
  → 大事情它能一直推进、断了能接着干（U6 大项目持续推进）
  → 干完了沉淀经验，下次更聪明（U7 收尾与沉淀）
```

这 7 块就是用户能**感知**到的全部。下面逐块从体验讲到底座。

---

## 2. 功能块逐块拆解

### U1 ｜我提一个目标

**用户做什么**：在输入框里写一句话，比如"给 Atelier 加上 DataProvider 支持"或"研究本季度科技股标的"。

**用户看到什么**：工作台没有立刻闷头干，而是先回给他一份**目标共识**——它理解的目标是什么、明确的非目标是什么、验收标准是什么，让他确认。

**这个功能块由什么组成（用户视角流程）**：
1. 用户输入原始目标。
2. 工作台发起一次多角色讨论，把模糊目标变成清晰契约（要什么、不要什么、怎么算完成）。
3. 把契约回显给用户确认/签字。

**底座怎么撑**：
- 目标录入 → `F-UI-01`
- "发起多角色讨论"→ 起一个 CollaborationTask、跑协作引擎 → `F-CL-01`、`F-CL-02`、`F-CL-03`
- "想清楚要什么/不要什么/怎么算完成"→ 生成 ProjectContract（goals / non_goals / acceptance）→ `F-PJ-01`
- "怎么算完成"必须可判定 → 每条验收标 L0/L1/L2 → `F-CO-10`、`F-CO-11`
- 用户确认签字 → `F-UI-03`（Goal Owner signoff）

---

### U2 ｜我看它给的计划

**用户做什么**：确认目标后，看工作台准备怎么干。

**用户看到什么**：一张**计划图**——大目标被拆成几个里程碑，里程碑下面是一条条具体任务，任务之间的先后依赖清清楚楚。他能看懂"它打算先做什么、后做什么、为什么这么拆"。

**这个功能块由什么组成**：
1. 把目标拆成里程碑树（Milestone Tree）。
2. 每个里程碑再拆成任务图（Task Graph），标好依赖。
3. 拆解有分歧时，内部讨论收敛到一个方案，并把"为什么这么拆"的依据留痕给用户看。

**底座怎么撑**：
- 拆里程碑 → `F-PJ-02`（Milestone Tree）
- 拆任务图 → `F-PJ-03` / `F-CL-06`（TaskGraph）
- 拆解的分歧收敛 → 共识收敛 + 反附和 → `F-CL-04`
- "为什么这么拆"的依据留痕 → 证据引用（evidence_ref，指向 Artifact）→ `F-CO-07`
- 计划由协作产出、再交给执行内核落地 → `F-CL-05`（Decision → Core 消费）

---

### U3 ｜我看它干活

**用户做什么**：点"开始"，然后就看着它干，不用一步步点。

**用户看到什么**：任务一条条自动往前跑，每条任务在调哪个工具（Codex / 数据源 / 研究工具）、跑出了什么日志、产出了什么文件（比如一个 `diff.patch`、一份 `result.json`），都实时可见、可点开。

**这个功能块由什么组成**：
1. 任务自动按依赖顺序进入执行。
2. 每条任务调用对应的外部工具（Provider）真实执行。
3. 执行产物（日志、文件、结果）被收集成 Artifact，可查看可下载。
4. 全过程状态自动流转，无需用户点每一步。

**底座怎么撑**：
- "调哪个工具"→ Provider 接入 + 路由 → `F-PR-01`、`F-PR-02`（coding）/`F-PR-03`（数据）、`F-CO-05`
- "真实执行一次"→ Run + Run 状态机 → `F-CO-02`
- "自动一条条跑"→ 执行循环 → `F-CO-06`、`F-CO-01`（Task 状态机）
- "产物可看可下"→ Artifact metadata projection + Host sandbox intent → `F-CO-07a` / `F-CO-07b`（metadata-only 已落；focused product-window safe body fetch 已补且 evidence 不含 raw `text`；artifactRendererSurface / runtimeLogStream / hostStorageAttachment 均有 `controlledEvidence`，其中 `artifactRendererSurface.controlledEvidence.liveWebviewProven=false`；rich renderer / Console Logs / attachment runtime 仍待 Host runtime/E2E）
- "改代码改在哪、不乱动别的"→ 工作区/沙箱 → `F-PR-05` ⚠️（WorkspaceOpenTarget / Host open intent 已接入；真实 IDE launch、workspace resolver、sandbox runtime 与 E2E 待验）
- "全程能回看"→ Trace → `F-FD-01`

---

### U4 ｜它自己查对错、自己修

**用户做什么**：基本不用做什么——这正是重点。

**用户看到什么**：一条任务跑完，工作台**自己跑检查**（编译/测试/数据质量等）。检查红了，它**自己改一轮再试**；改好了就继续。用户只是看到"失败 → 自动修 → 通过"这个过程，不用插手。如果它反复修都修不动，才停下来标记。

**这个功能块由什么组成**：
1. 任务产出后自动跑质量门禁（Gate）。
2. 门禁不过 → 阻断，不让它假装"完成"。
3. 自动回到执行环节修复，再跑门禁。
4. 修复有上限：超过次数 / 原地打转无进展 → 停下来升级，不无限烧钱。
5. 门禁全过 → 自动验收通过。

**底座怎么撑**：
- "自己跑检查"→ Gate 框架 + coding/domain gates → `F-GT-01`、`F-GT-02`、`F-GT-03`
- "红了就不让过"→ block 阻断 + 回灌 → `F-GT-05`
- "自己改一轮"→ Fix Loop → `F-CO-09`
- "修不动就停"→ 无进展检测 + 上限 → `F-CO-09`（含 Fix 硬约束）
- "自动判定通过"→ Verifier（L0/L1 自动）+ 完成谓词 → `F-CO-10`、`F-CO-11`

---

### U5 ｜该问我时才问我

**用户做什么**：平时不被打扰；只在工作台**真的需要他决策**时收到一条带上下文的请求。

**用户看到什么**：大部分时间它自己干。但遇到这几类情况，它会**停下来问他**，并且把"为什么停、花了多少、有哪些选项、推荐哪个、有什么后果"一次讲清楚：
- 目标有冲突，它自己定不了；
- 要做危险/不可逆的事（删库、发布、下单）；
- 权限不够；
- 反复试都过不了验收；
- 花的钱/时间超过了上限；
- 遇到需要人主观判断的活（研究结论好不好）。

**这个功能块由什么组成**：
1. 危险动作被硬拦，不许自动执行。
2. 成本/时间触顶被熔断。
3. 主观任务（L2）到验收点必须交给人。
4. 升级时附完整决策信息。

**底座怎么撑**：
- "危险/不可逆动作硬拦"→ Policy 引擎 + Escalation Guard → `F-FD-03`、`F-CL-10`、`F-PR-04`（高危动作单列）
- "花超了就停"→ Budget 熔断 → `F-FD-02`
- "主观活交给人"→ L2 Verifier 强制人工 → `F-CO-10`
- "升级条件"→ Human-in-loop 触发 → `F-HL-01`
- "把决策信息讲清楚"→ 升级载荷（证据/成本/选项/推荐/回滚影响）→ `F-HL-02` ✅（typed payload + route normalization service/static 已落；真实 E2E 未证明）
- 用户做决策 → `F-UI-03`

---

### U6 ｜大事情它能一直推进、断了能接着干

**用户做什么**：交给它一个大项目，可以关掉页面去睡觉。

**用户看到什么**：回来时项目又往前走了一截。它不会卡在某一步干等，也不会因为中途断电/熔断就从头再来——它从**上次完成的地方**接着干，已经做完验收过的部分不重做。如果原来的计划过时了，它会**重新规划**并告诉用户。

**这个功能块由什么组成**：
1. 有个"监工"持续巡查，发现卡住/跑偏/死锁就处理，并把就绪的任务推进下去。
2. 计划过时 → 自动重规划，签字后替换。
3. 中断后能从最近一个完成锚点恢复，已完成产物复用。
4. 里程碑逐个验收通过，项目逐步逼近完成。

**底座怎么撑**：
- "监工持续巡查推进"→ Supervisor Loop（+EventBus 驱动）→ `F-CL-07` / `F-FD-05` ⚠️（schema + supervisor tick/sweep + scheduler service/static 已落；真实运行时 E2E 待验）
- "计划过时就重规划"→ Replan 机制 → `F-CL-08` ⚠️（已前移到 B9.5 并接入 supervisor replan interrupt；真实运行时/E2E 待验）
- "断了从锚点接着干"→ Resume / 恢复锚点 + 幂等重放 → `F-CO-12` / `F-CO-13` ⚠️（已前移并绑定 accepted anchor；真实跨重启恢复 E2E 待验）
- "里程碑逐个验收"→ Milestone/Project 状态机 + 验收 → `F-CO-03`、`F-CO-04`、`F-PJ-04`
- "并行任务结果合并不打架"→ Integrator → `F-CL-09` ⚠️（`integrator_required` + Station integrator identity 前置条件已定；真实 merge runtime/E2E 未落）

---

### U7 ｜干完了，沉淀经验

**用户做什么**：项目收尾时，花一分钟确认几条"经验"。

**用户看到什么**：工作台给出一份**收尾报告**（做完了什么、还剩哪些风险、有哪些后续待办），以及几条**经验候选**（这次成功的范式、失败的原因、该记住的项目规则）。用户**勾选确认**哪些值得长期记住，下次它就更聪明——但不确认的不会自动塞进记忆。

**这个功能块由什么组成**：
1. 全部里程碑验收 → 项目验收 → 完成判定。
2. 自动生成收尾报告 + 残余风险 + follow-up。
3. 自动产出经验候选，用户确认后才入长期记忆。

**底座怎么撑**：
- "项目验收完成"→ Project Verification/Acceptance + 完成谓词 → `F-PJ-05`、`F-CO-11`
- "残余风险/后续待办"→ Residual Risk / Blocker → `F-PJ-06` / `F-PJ-07` ⚠️（formal proto + read-only projection 已补；Station governance runtime/E2E 待落）
- "经验候选"→ Memory Candidate 生成 → `F-MM-01`
- "确认才记住"→ 两阶段写入 → `F-MM-02`、`F-UI-04`
- "下次更聪明"→ 失败记忆反哺 Planner/Risk → `F-MM-03` ✅（feedback policy feeds 已输出；真实 Planner/Risk/Verifier 反哺消费 E2E 未验）

## 3. 一张图：用户功能块 ↔ 底座域

```
用户功能块（看得见）          底座域（看不见，feature-matrix）
─────────────────────────────────────────────────────
U1 提目标          ──► Collaboration(F-CL) + Project(F-PJ) + UI(F-UI)
U2 看计划          ──► Collaboration(F-CL) + Project(F-PJ)
U3 看它干活        ──► Provider(F-PR) + Core(F-CO) + Foundation(F-FD)
U4 自查自修        ──► Gate(F-GT) + Core(F-CO)
U5 该问才问        ──► Foundation/Policy(F-FD) + Collaboration(F-CL) + HL(F-HL)
U6 持续推进/恢复   ──► Collaboration(F-CL) + Core(F-CO)
U7 收尾沉淀        ──► Project(F-PJ) + Memory(F-MM)
```

**读法**：左边是用户能感知的 7 件事，右边是支撑它的底座域。每个底座功能点（F-XX）只为某个用户功能块服务——**底座的存在理由都能在用户视角找到出处**。如果某个底座功能点对不上任何 U，它就是过度设计；如果某个 U 落不到底座，它就是空承诺。

## 4. 用户功能块 ↔ 积木阶段

把"用户能做的事"和 [roadmap.md](./roadmap.md) 的积木阶段对上，看每个阶段用户能体验到第几块：

| 用户功能块 | 最早可体验阶段 | 说明 |
|-----------|--------------|------|
| U3 看它干活（单任务） | 检查点 A | 先有"它能自己干一条任务" |
| U4 自查自修 | 检查点 A | A 阶段就闭环 |
| U5 该问才问 | 检查点 A | 预算/危险闸在 A 阶段 |
| U1 提目标 / U2 看计划 | 检查点 B | 协作拆解到位后才有"目标→计划" |
| U6 持续推进/恢复 | 检查点 B | 项目级推进 + 恢复 |
| U7 收尾沉淀 | 检查点 B | 经验沉淀 |
| （U1–U7 跨领域：数据/研究/交易） | 检查点 C/D | 换形状不换地基 |

> 注意：U1/U2（提目标、看计划）虽然在用户体验上是"第一步"，但底座上要**等协作拆解（检查点 B）才齐**。检查点 A 阶段用户其实是"直接喂一条明确任务"，体验从 U3 开始。这正是"积木式"的取舍：先把最里面的执行闭环搭实，再往外补"目标→计划"这层壳。
